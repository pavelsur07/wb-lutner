# ТЗ. Интеграция Lutner ↔ Wildberries / Ozon

Документ описывает, как система взаимодействует с поставщиком (Lutner) и
маркетплейсами: получение остатков, обновление остатков, оформление заказов,
обработка ошибок. Сценарии описаны с точки зрения поведения системы
(клиентские сценарии) и снабжены чек-листами проверки готовности.

Версия описывает **фактически реализованное** поведение на 09.2026, включая
известные ограничения.

---

## 1. Топология и роли

```
                 CSV полный прайс (сутки)          Rest API (заказы)
  ┌──────────┐  ──────────────────────────►  ┌──────────────┐
  │          │                                │              │
  │  LUTNER  │  ── webhook остатков (5 мин) ►│    СИСТЕМА   │
  │          │                                │  (VPS, SQLite)│
  └──────────┘  ◄── POST /order/ ────────────│              │
                                              └───┬──────┬───┘
                                                  │      │
                              остатки/заказы ─────┘      └───── остатки/заказы
                                    ▼                                ▼
                            ┌───────────────┐              ┌───────────────┐
                            │  WILDBERRIES  │              │     OZON      │
                            │  склад FBS    │              │  склад FBS    │
                            └───────────────┘              └───────────────┘
```

**Инфраструктура:** Ubuntu VPS, `/opt/wb-lutner`, пользователь `wblutner`,
Python 3.12 + venv, SQLite (WAL), Flask + Gunicorn + Nginx + Let's Encrypt,
домен `lutner.conwix.ru`, задачи по расписанию — cron + flock.

**Направление данных:**

| Поток | Источник | Приёмник | Периодичность |
|---|---|---|---|
| Справочник товаров | Lutner (CSV) | БД `catalog` | 1 раз в сутки, 03:00 |
| Остатки и цены | Lutner (webhook) | БД `stock` | каждые 5 мин (push от Lutner) |
| Остатки | БД | WB / Ozon | каждые 10 мин |
| Заказы | WB / Ozon | БД → Lutner | каждые 5 мин |
| Связки товаров | WB / Ozon | БД `mapping` / `ozon_mapping` | каждые 15 мин |

## 2. Ключи связывания товаров

Единый принцип для обеих площадок — **связка по артикулу поставщика**.

| Система | Поле | Соответствие |
|---|---|---|
| Lutner | `IP_PROP96` → `catalog.article` | эталон |
| Wildberries | `vendorCode` карточки | `= catalog.article` |
| Ozon | `offer_id` товара | `= catalog.article` |

**Важное различие.** Связка строится по артикулу, но **отправка остатков**
использует разные идентификаторы:

- **WB** принимает остатки только по `sku` (баркод карточки WB). Система
  получает баркод из карточки автоматически при маппинге и хранит в
  `mapping.wb_barcode`. Баркод Lutner (`IP_PROP95`) для WB **не используется**.
- **Ozon** принимает остатки по `offer_id` — то есть по тому же артикулу.

## 3. Сценарий 1. Получение остатков от Lutner

### 3.1 Основной поток — webhook

**Триггер:** Lutner отправляет POST на публичный HTTPS-эндпоинт каждые 5 минут.

**Эндпоинт:** `https://lutner.conwix.ru/webhook/stock/<секрет>`
Секрет хранится в `.env` (`WEBHOOK_SECRET_PATH`), в URL не предсказуем.

**Формат входящих данных:** JSON-массив, только изменившиеся позиции (дельта),
а не весь каталог.

```json
[{"id":"uuid","quantity":10,"store_spb":7,"store_ekb":3,
  "price_retail":780,"price_diller":497,"price_mp":936}]
```

**Поведение системы:**

1. Проверяет, что тело — массив. Если нет — фиксирует ошибку, но отвечает 200.
2. Открывает транзакцию, для каждой позиции делает upsert в `stock` по `uuid`.
3. **Некорректная позиция не прерывает батч** — она пропускается с записью в
   лог, остальные сохраняются (статус батча `partial`).
4. Обновляет `system_state.last_stock_webhook`.
5. Пишет строку в `webhook_log`: IP, X-Forwarded-For, User-Agent, размер тела,
   количество позиций, статус, текст ошибки.
6. **Всегда возвращает HTTP 200** — иначе Lutner повторяет доставку и присылает
   дубли.

### 3.2 Вспомогательный поток — суточный прайс

**Триггер:** cron, 03:00 МСК.
**Источник:** полный прайс CSV (UTF-8, разделитель `;`, ~53 000 строк, ~30 МБ).

Полный прайс — единственный источник **штрих-кодов**, габаритов и веса;
краткий прайс их не содержит.

**Поведение:**

1. Скачивание с таймаутом 300 с.
2. **Защита от пустого файла:** если 0 строк — прерваться и алертить,
   справочник не обнулять.
3. В одной транзакции: сбросить `active=0` у всех, затем upsert каждой строки
   с `active=1` (или `0`, если заполнено `IP_PROP140` — снят с производства).
4. Обновить `system_state.last_catalog_sync`.

### 3.3 Контроль живости

`check_heartbeat.py`, cron каждые 10 минут: если `last_stock_webhook` старше
**15 минут** — письмо на `ALERT_TO`. Отсутствие записи вовсе — тоже алерт.

### Чек-лист готовности — получение остатков

- [ ] `curl https://lutner.conwix.ru/health` → `{"status":"ok"}`
- [ ] Сертификат валиден, автопродление: `certbot renew --dry-run` → success
- [ ] Тестовый POST на webhook возвращает 200 и создаёт строку в `stock`
- [ ] Неверный секрет в URL → 404
- [ ] Кривая позиция в батче не ломает остальные (статус `partial`)
- [ ] `webhook_log` пополняется, в нём виден IP отправителя
- [ ] `SELECT COUNT(*) FROM stock` растёт со временем
- [ ] `sync_catalog.py` наполняет `catalog`, доля строк со штрих-кодом ожидаемая
- [ ] `check_heartbeat.py` при свежем webhook пишет `heartbeat ok`
- [ ] Через 2–3 дня: по `webhook_log` определить IP Lutner и добавить allowlist
      в nginx

## 4. Сценарий 2. Обновление остатков на маркетплейсах

### 4.1 Правила расчёта отправляемого остатка

Источник — **только склад Санкт-Петербург** (`stock.store_spb`). Склад
Екатеринбурга (`store_ekb`) сохраняется в БД, но на маркетплейсы не передаётся.

Последовательность преобразований:

| Шаг | Правило | Причина |
|---|---|---|
| 1 | `amount = max(0, store_spb)` | Lutner присылает отрицательные значения; WB отклоняет весь батч |
| 2 | `amount < MIN_STOCK_THRESHOLD → 0` | страховка от оверселла; порог в `.env`, текущее значение **5** |
| 3 | отсутствует запись в `stock` → `0` | товара нет в остатках |

Порог единый для обеих площадок.

### 4.2 Wildberries

**Метод:** `PUT /api/v3/stocks/{warehouseId}`, батч до 1000 позиций.
**Склад:** `WB_WAREHOUSE_ID` (текущий — `1851905`, «FBS Лютнер»).

Особенности поведения:

- WB **отклоняет весь батч** (409 Conflict), если в нём есть хотя бы один `sku`,
  не заведённый на складе. Поэтому при ошибке батча система
  **переходит на поштучную отправку**: известные товары проходят, новые
  привязываются к складу, а не поддающиеся — попадают в список отклонённых.
- По умолчанию перед отправкой выполняется проверка привязки
  (`POST /api/v3/stocks/{warehouseId}` со списком sku): товары, которых склад
  не знает, пропускаются молча.
- Флаг `--no-filter` отключает эту проверку — режим «прогрева» новых товаров.
- Флаг `--only <артикул|баркод>` — работа с одной позицией.

### 4.3 Ozon

**Метод:** `POST /v2/products/stocks`, батч **до 100** пар «товар–склад».
**Склад:** `OZON_WAREHOUSE_ID` (текущий — `1020005028184660`, «Лютнер FBS»).

Особенности:

- Ozon заводит связь «товар–склад» **автоматически** при первой отправке
  остатка. Предварительная привязка в кабинете не требуется.
- Ответ содержит результат по каждой позиции (`updated`, `errors`) — ошибка
  одной позиции не влияет на остальные.
- Есть ограничение частоты обновления **одного товара**: повторный ручной
  запуск сразу после планового вызывает `TOO_MANY_REQUESTS`. Запускать
  синхронизацию вручную поверх cron не следует.

### 4.4 Обработка ошибок

| Код / текст | Площадка | Причина | Реакция системы |
|---|---|---|---|
| `IncorrectRequestBody` | WB | отрицательный остаток в батче | предотвращено правилом `max(0, …)` |
| `409 Conflict` | WB | в батче есть sku, не заведённый на складе | переход на поштучную отправку |
| `409 Conflict` | WB | повторное добавление задания в поставку | предотвращено проверкой состава поставки (`order-ids`) |
| `404 path not found` | WB | метод отключён/переименован WB (случай 03.09.2026: `/api/v3/supplies/{id}/orders/{orderId}`) | алерт о застрявших `pending_supply`, сверка с актуальной документацией |
| `404 NotFound` | WB | склад удалён или неверный ID | алерт, требуется обновить `WB_WAREHOUSE_ID` |
| `PRODUCT_IS_ARCHIVED` | Ozon | товар в архиве | позиция пропущена, алерт; разбор в кабинете |
| `TOO_MANY_REQUESTS` | Ozon | слишком частое обновление товара | пропуск до следующего цикла |
| `401 token scope` | оба | ключу не хватает прав | алерт, перевыпуск ключа |
| сетевая ошибка / 5xx | оба | временный сбой | retry с задержкой 2/4/8 с |

**Общий принцип:** частичная неудача не останавливает цикл; итог каждого
прогона фиксируется в логе и в `system_state`.

### Чек-лист готовности — обновление остатков

- [ ] `--dry-run` показывает корректный список без отправки
- [ ] Позиции с остатком ниже порога отображаются как `0`
- [ ] Отрицательные значения преобразуются в `0`
- [ ] Реальный прогон завершается `pushed N … (ошибок: 0)`
- [ ] Контрольная сверка: остаток в Lutner = остаток в кабинете маркетплейса
- [ ] Новый товар после первой отправки появляется на складе площадки
- [ ] Cron выполняется каждые 10 минут, логи без ошибок
- [ ] `system_state.last_stock_to_wb` / `last_stock_to_ozon` обновляются
- [ ] При искусственной ошибке приходит письмо на `ALERT_TO`

## 5. Сценарий 3. Связывание товаров (маппинг)

**Триггер:** cron каждые 15 минут, отдельно для каждой площадки.

**Логика (одинаковая для WB и Ozon):**

1. Постранично получить все карточки площадки.
2. Взять артикул продавца (`vendorCode` / `offer_id`).
3. Найти в `catalog` товар с таким `article`.
4. Совпадение есть → upsert связки; для WB дополнительно сохраняется баркод
   карточки (`sku`) и `nmID`, для Ozon — `product_id` и `sku`.
5. Совпадения нет → позиция пропускается и попадает в лог как «артикул не
   найден в каталоге Lutner» (это товары других поставщиков — нормальная
   ситуация).

Операция **идемпотентна**: повторный запуск обновляет существующие связки и
добавляет новые, ничего не удаляя.

### Чек-лист готовности — маппинг

- [ ] Новый товар, заведённый на площадке с артикулом Lutner, появляется в
      связках в течение 15 минут
- [ ] Товары других поставщиков не попадают в связки
- [ ] Повторный запуск не создаёт дублей
- [ ] Количество связок соответствует ожидаемому ассортименту

## 6. Сценарий 4. Оформление заказа Wildberries

Порядок принципиален: **сначала поставка и стикер, только потом заказ в
Lutner** — номер стикера должен попасть в комментарий.

**Триггер:** cron каждые 5 минут.

### Шаги

1. **Получение заданий:** `GET /api/v3/orders/new`.
2. **Фильтрация по складу:** обрабатываются только задания, у которых
   `warehouseId` совпадает с нашим. Задания других складов продавца
   пропускаются (пишется количество пропущенных).
3. **Идемпотентность:** задание пропускается, если уже имеет финальный статус
   (`created`, `no_mapping`, `dry_run`, `manual`). Промежуточные состояния
   (`pending_supply`, `failed`) обрабатываются повторно. Статус `manual` —
   заказ обработан вручную вне системы, автоматика его не трогает.
4. **Определение товара:** по `skus[0]` находится связка в `mapping`,
   из неё — артикул Lutner и остаток по СПб.
5. **Проверка остатка:** если `store_spb < количества` — заказ не создаётся,
   фиксируется статус `no_stock` либо `ekb_only` (если товар есть в
   Екатеринбурге), отправляется алерт для ручного разбора.
6. **Поставка:**
   - найти активную (незакрытую) поставку с именем `Лютнер <дата отгрузки>`;
   - если её нет — создать (`POST /api/v3/supplies`);
   - проверить состав поставки
     (`GET /api/marketplace/v3/supplies/{supplyId}/order-ids`) и, если задания
     там ещё нет, добавить его
     (`PATCH /api/marketplace/v3/supplies/{supplyId}/orders`, тело
     `{"orders": [id]}`) — задание переходит в статус «На сборке».
     Проверка состава обязательна: повторное добавление уже привязанного
     задания даёт 409, который WB считает как 10 запросов лимита.
     Старый метод `PATCH /api/v3/supplies/{id}/orders/{orderId}` WB отключил
     (404) — обновлено 08.09.2026.
7. **Стикер:** `POST /api/v3/orders/stickers` → части `partA` и `partB`.
8. **Комментарий:** `Wildberries, отгрузка DD.MM.YYYY, Стикер <partA> <partB>`.
9. **Заказ в Lutner:** `POST /order/` (состав см. раздел 8).
10. **Фиксация:** статус `created`, сохраняется `lutner_order_id`.

**Обработка сбоя на шагах 6–7:** заказ в Lutner **не создаётся**, задание
получает статус `pending_supply` и повторяется в следующем цикле. Это защищает
от заказа без номера стикера.

**Ограничения и договорённости:**

- Поставки формируются **только автоматически**. Ручное создание поставок
  в кабинете приведёт к дублям на одну дату и расхождению состава.
- Отдельного метода «подтвердить задание» у FBS нет: перевод в сборку
  происходит именно через добавление в поставку.

### Чек-лист готовности — заказы WB

- [ ] `--dry-run` корректно разбирает реальные задания
- [ ] Задания чужих складов пропускаются
- [ ] Первый заказ дня создаёт поставку `Лютнер <дата>`
- [ ] Второй заказ той же даты попадает в **ту же** поставку
- [ ] После добавления в поставку задание переходит в «На сборке»
- [ ] Стикер получен, номер присутствует в комментарии Lutner
- [ ] Заказ создан в Lutner, `lutner_order_id` сохранён в БД
- [ ] Повторный запуск не создаёт дубль заказа
- [ ] При недоступности стикера заказ в Lutner не создаётся, статус
      `pending_supply`, следующий цикл доводит до конца
- [ ] Состав поставки в кабинете WB соответствует заказам в Lutner

## 7. Сценарий 5. Оформление заказа Ozon

**Триггер:** cron каждые 5 минут.

### Шаги

1. **Получение отправлений:** `POST /v3/posting/fbs/unfulfilled/list`.
   В фильтре **обязателен** период `cutoff_from` / `cutoff_to`, иначе
   запрос отклоняется.
2. **Фильтрация по складу:** обрабатываются только отправления, у которых
   `delivery_method.warehouse_id` совпадает с нашим.
3. **Идемпотентность** по `posting_number` (строка, не число).
4. **Состав отправления:** отправление может содержать **несколько позиций**.
   Для каждой находится связка и проверяется остаток по СПб.
5. **Проверка остатка:** если хотя бы одна позиция недоступна — заказ **не
   создаётся целиком**, статус `failed`, алерт с перечнем проблемных позиций.
6. **Комментарий:** `Ozon, отгрузка DD.MM.YYYY, Отправление <posting_number>`.
7. **Заказ в Lutner:** одно отправление → **один** заказ со всеми позициями.
8. **Фиксация:** статус `created`, сохраняется `lutner_order_id`.

### Чек-лист готовности — заказы Ozon

- [ ] Запрос отправлений проходит (период cutoff задан)
- [ ] Отправления чужих складов пропускаются
- [ ] Многотоварное отправление создаёт **один** заказ со всеми позициями
- [ ] Номер отправления присутствует в комментарии
- [ ] Отсутствие остатка по любой позиции блокирует весь заказ и даёт алерт
- [ ] Повторный запуск не создаёт дубль

## 8. Сценарий 6. Резервирование товара в Lutner

**Важное уточнение.** Отдельного метода бронирования у Lutner нет.
**Резервирование = создание заказа на розничную сборку.** До момента создания
заказа товар не закреплён за нами и может быть продан Lutner в другом канале.

**Запрос:** `POST https://lutner.ru/local/api/order/`
**Авторизация:** заголовок `Api-token`.

```json
{
  "profile": 2943,
  "warehouse": "<UUID склада отгрузки>",
  "dropshipping": true,
  "dropshipping_count": 1,
  "items": {"<артикул>": <количество>},
  "comment": "<площадка>, отгрузка DD.MM.YYYY, <идентификатор>"
}
```

**Ответ:**

```json
{"order_id": 1037322, "errors": []}
```

При отказе `order_id` равен `null`, а `errors` содержит список причин
(например, неизвестный артикул или отсутствие остатка). Система различает эти
случаи: успех → статус `created`; наличие `errors` → статус `failed` и алерт.

**Ограничения Lutner:**

| Параметр | Значение | Реализация |
|---|---|---|
| Запросов в минуту | 10 | ограничитель 8/60 с (скользящее окно) |
| Запросов в сутки | 500 | дневной счётчик, потолок 480 |
| Дедлайн приёма «день в день» | 08:00 МСК | учитывается в правиле даты |
| Баланс юрлица | должен быть положительным | контроль вне системы |

Суточная квота — **общая на обе площадки**. При её исчерпании система
останавливается и отправляет алерт, приоритет площадкам не назначается.

### Правило даты отгрузки

Единое для WB и Ozon, вычисляется от времени создания заказа на площадке
(время приходит в UTC, приводится к МСК):

1. Заказ до **07:00 МСК** включительно → отгрузка **сегодня**.
2. Заказ после **07:01 МСК** → отгрузка **следующего дня**.
3. Если полученная дата приходится на субботу или воскресенье → переносится
   на **понедельник**.

Праздничные дни не учитываются — при необходимости требуется доработка.

### Чек-лист готовности — резервирование

- [ ] Тестовый запрос с несуществующим артикулом возвращает `errors`,
      реальный заказ не создаётся
- [ ] Поле `warehouse` принимается площадкой (UUID склада)
- [ ] Успешный ответ содержит `order_id`, он сохраняется в БД
- [ ] Ограничитель не допускает превышения 10 запросов в минуту
- [ ] При приближении к суточной квоте отправляется алерт
- [ ] Дата отгрузки соответствует правилу (проверить границы 07:00 / 07:01
      и пятницу после 07:00 → понедельник)
- [ ] Комментарий содержит площадку, дату и идентификатор заказа/стикера

## 9. Уведомления и контроль

| Событие | Канал | Реализовано |
|---|---|---|
| Сбой синхронизации остатков | письмо на `ALERT_TO` | да |
| Отказ Lutner при создании заказа | письмо | да |
| Отсутствие остатка по заказу | письмо | да |
| Заказы WB застряли в `pending_supply` > 2 ч | письмо (не чаще раза в 6 ч) | да |
| Молчание webhook > 15 мин | письмо | да |
| Сводка за сутки (20:00) | письмо | да |
| Утреннее письмо менеджеру Lutner к 08:00 | письмо с составом и этикетками | **нет, отправляется вручную** |

**Требование Lutner к утреннему письму:** одно письмо на одну площадку,
тема — наименование юрлица, площадка, дата отгрузки; вложения — состав
отгрузки, этикетки, акт. Срок — до 08:00 МСК.

## 10. Известные ограничения

1. **Утренние письма менеджеру не автоматизированы** — ни для WB, ни для Ozon.
2. **Крупногабаритные товары** не принимаются текущим складом WB: система
   работает с одним складом, разделение по типу груза не реализовано.
3. **Склад Екатеринбурга** не используется для отгрузки; при наличии товара
   только там заказ помечается `ekb_only` и требует ручного разбора.
4. **Праздничные дни** в правиле даты отгрузки не учитываются.
5. **Баланс Lutner** автоматически не проверяется — отдельного метода нет.
6. **Панель администратора** не реализована.
